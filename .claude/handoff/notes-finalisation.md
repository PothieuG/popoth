## 2. Vérifier que la base dev est identique à la prod (demande explicite de l'utilisateur)

Comparer les schémas **réels** des deux bases (lecture seule sur les deux) :

```powershell
New-Item -ItemType Directory -Force tmp | Out-Null
$env:SUPABASE_PROJECT_REF = $null
node scripts/export-schema.mjs tmp/schema-prod.sql
$env:SUPABASE_PROJECT_REF = 'ddehmjucyfgyppfkbddr'
node scripts/export-schema.mjs tmp/schema-dev.sql
$env:SUPABASE_PROJECT_REF = $null
git diff --no-index --stat tmp/schema-prod.sql tmp/schema-dev.sql
git diff --no-index tmp/schema-prod.sql tmp/schema-dev.sql
```

- Ignorer les lignes d'en-tête `-- Generated by ...` et `-- Project: ...` (elles diffèrent toujours).
- Compléter par les fonctions et la RLS, sur les deux bases :
  ```powershell
  pnpm db:check-rpcs; pnpm db:check-rls
  $env:SUPABASE_PROJECT_REF = 'ddehmjucyfgyppfkbddr'; pnpm db:check-rpcs; pnpm db:check-rls; $env:SUPABASE_PROJECT_REF = $null
  ```
- `export-schema.mjs` ne capture **pas** les corps de fonctions ni les event triggers : c'est
  `db:check-rpcs` / `db:check-rls` qui couvrent ce trou.

**Si des écarts existent** : les lister à l'utilisateur en langage clair (« la base de test n'a pas
la colonne X », « la fonction Y manque »), retrouver dans `supabase/migrations/` le(s) fichier(s)
qui les créent, et **proposer** de les appliquer sur dev via `apply-sql.mjs` (dev n'a pas de
tracker `schema_migrations`, cf. [multi-env.md](../conventions/multi-env.md) §6). N'appliquer
qu'après accord. Si un écart va dans l'autre sens (dev a quelque chose que la prod n'a pas), le
signaler sans rien supprimer.

Les fichiers `tmp/*.sql` ne doivent pas être commités (vérifier `git status`, supprimer à la fin).

## 3. Appliquer la migration Notes sur dev

Après confirmation de l'utilisateur :

```powershell
$env:SUPABASE_PROJECT_REF = 'ddehmjucyfgyppfkbddr'
node scripts/apply-sql.mjs supabase/migrations/20260923000000_create_notes.sql
```

Attendu : `HTTP 201`. Puis vérifier (fichier temporaire, non commité) :

```powershell
@"
SELECT c.relname, c.relrowsecurity,
       (SELECT count(*) FROM pg_policies p WHERE p.tablename = 'notes') AS policies,
       (SELECT array_agg(conname ORDER BY conname) FROM pg_constraint WHERE conrelid = c.oid) AS constraints
FROM pg_class c WHERE c.relname = 'notes' AND c.relnamespace = 'public'::regnamespace;
"@ | Set-Content tmp/check-notes.sql
node scripts/apply-sql.mjs tmp/check-notes.sql
pnpm db:check-rls
$env:SUPABASE_PROJECT_REF = $null
```

Attendu : `relrowsecurity = true`, `policies = 0`, contraintes `notes_pkey`, `notes_profile_id_fkey`,
`notes_group_id_fkey`, `notes_created_by_profile_id_fkey`, `notes_content_not_empty_check`,
`notes_content_max_len_check`, `notes_owner_exclusive_check`.

```powershell

```

`pnpm test:run` doit donner 1030 tests passants (254 ignorés). Puis, dans le navigateur en vue
mobile (DevTools, iPhone ≤ 430 px), avec un compte de test **membre d'un groupe** :

1. Dashboard perso : la ligne `Économies (montant)` | `Notes` s'affiche, montant entier.
2. Ouvrir Notes → ajouter une note → elle apparaît avec « Vous » et l'avatar ; le compteur passe à 1.
3. Modifier puis supprimer la note (confirmation demandée).
4. Dashboard groupe : ajouter une note. Se connecter avec un **2e membre** du même groupe
   (autre navigateur / navigation privée), tirer l'écran vers le bas : la note apparaît avec
   l'avatar et le prénom du 1er membre ; le 2e membre peut la modifier et la supprimer.
5. Vérifier qu'une note perso du membre 1 n'est **pas** visible par le membre 2.
6. Note vide → message « La note ne peut pas être vide » ; rien n'est envoyé.

Si un bug apparaît : le corriger sur `g_/peaceful-fermi-h579eu`, avec test, puis
`pnpm typecheck; pnpm lint:check; pnpm format:check; pnpm test:run` avant commit.
